# السياسات ومراجعة المكافآت — الدورة الأولى

من قائمة الحساب افتح **السياسات والموافقات**. هذه مراجعة حتمية بالكود تعتمد على بيانات الشركة وسياسة أدخلها مدير مخوّل. الأسباب عربية ومثبتة مع الأدلة؛ لم يُربط نموذج AI بهذا المسار، ولا يحرك أموالاً أو يعدّل التعويض أو مسير الرواتب.

## الإعداد والصلاحيات

بعد التحديث نفّذ migrate وdb:seed وteami:permissions:sync-owners كما في UPDATE-INSTRUCTIONS.md، مع الحفاظ على APP_KEY وAUDIT_HMAC_KEY. المالك الحالي يوزع الصلاحيات حسب المسؤوليات؛ لا يرفع ملفات الشركة لكل الموظفين.

كل مسارات المكافآت تحتاج advisor.bonus.read + data.sensitive.read + hr.compensation.read، لأنها تقرأ لقطة تتضمن الأساس السنوي. إنشاء السياسة يحتاج أيضاً advisor.policy.manage؛ تقديم الطلب advisor.bonus.submit؛ إعادة التقييم والقرار advisor.bonus.approve؛ تجاوز سياسة إلزامية advisor.bonus.override. صلاحية الموافقة لا تمنح حق التجاوز تلقائياً. يظل مقدم الطلب ممنوعاً من اتخاذ القرار حتى لو كان مالك الشركة.

1. استورد الموظفين والعملاء والفواتير والتحصيلات والمرتجعات.
2. استورد هدف الموظف بنفس العملة وبنفس بداية ونهاية فترة الطلب. لا نجزّئ أو نجمع أهداف فترات أخرى ولا نستعمل قيمة actual المدخلة يدوياً في CRM.
3. أدخل أو استورد تعويضاً سنوياً واحداً بنفس العملة يغطي الفترة كاملة. لا نجمع عقود رواتب مختلفة أو بدلات أو تغيرات داخل الفترة. الاستيراد لا يغلق سجلاً سابقاً.
4. أنشئ سياسة بنسبة تحقيق الهدف المطلوبة، ونسبة التحصيل، وسقف المكافأة كنسبة من أساس شهر. النسب قرارات الشركة؛ لا توجد قواعد عمل مفترضة مسبقاً.
5. قدّم الطلب ثم يقرأ مدير مستقل الأسباب والأدلة قبل الموافقة أو الرفض.

اختيار الموظف في نموذج الطلب يعرض أول 100 موظف عند امتلاك hr.employee.read. دون هذه الصلاحية يُدخل UUID الموظف. اختيار السياسة من الصفحة الحالية للقائمة؛ استخدم الترقيم للوصول إلى النسخة المطلوبة. البحث الموسع واختبار السياسة قبل تفعيلها وإجراءات سحب السياسة مراحل لاحقة.

## السياسة والإصدار

السياسة تتضمن الاسم، إصداراً متزايداً لنفس الاسم، العملة، فترة السريان، النمط، والقواعد. إنشاؤها يتيح استخدامها مباشرة؛ لا توجد مرحلة مسودة أو اختبار تفعيل. لا توجد واجهة تعديل أو حذف للنسخة. كل طلب يختار UUID النسخة صراحة، ويجب أن تغطي كامل فترة الطلب. إنشاء نسخة جديدة لا يغيّر طلباً سابقاً. يمكن إدخال سياسة لفترة تاريخية يختارها مدير الشركة، ولا ندّعي أنها كانت قائمة فعلاً قبل وقت إدخالها.

- minimum_sales_percent: من 0 إلى 1000، حتى منزلتين.
- minimum_collection_percent: من 0 إلى 100، حتى منزلتين.
- maximum_monthly_base_percent: أكبر من 0 وحتى 1000، حتى منزلتين.
- advisory: المدير المستقل يستطيع قبول الاعتراض أو نقص البيانات بسبب موثق؛ يسجل القرار كتجاوز.
- enforced: أي اعتراض أو نقص بيانات يمنع الموافقة إلا مع advisor.bonus.override وسبب موثق. الرفض لا يحتاج صلاحية تجاوز.

## الحساب والتفسير

نفس مجموعة فواتير فترة الطلب، والتحصيلات والمرتجعات حتى as_of، كما في ADVISOR-METRICS.md. صافي المبيعات = قيم الفواتير ناقص المرتجعات المسجلة. تحقيق الهدف = الصافي ÷ الهدف ×100. نسبة التحصيل = التحصيل المسجل ÷ الصافي ×100؛ غياب صافي موجب يمنع حسابها. الرصيد الدائن بعد المرتجعات يحتاج مصالحة قبل الحكم على المكافأة.

السقف = floor(الأساس السنوي بوحدات العملة الصغرى × نسبة السقف ÷ 1200). مثال اختباري: أساس سنوي 1200 USD ونسبة 10% تعني سقف 10 USD. السقف نسبة من أساس شهر واحد دائماً؛ لا يُضرب بعدد أشهر فترة الطلب ولا يستنتج قواعد أجور قانونية. التقريب للأسفل إلى سنت USD أو فلس IQD. المقارنة المالية والحدود تستخدم bcmath ووحدات صحيحة، لا float؛ النسب المعروضة مقطوعة إلى منزلتين بينما اختبار الحد يستخدم الضرب الدقيق.

لكل شرط code وlevel: met / objection / missing، وتفسير عربي يذكر النسب أو مبلغ الطلب والسقف. الهدف المفقود والتعويض غير الصالح والموظف غير النشط لها أسباب واضحة. اكتمال ملفات الشركة غير مؤكد دائماً في هذه النسخة: **لا توجد نتيجة موافقة آلية**؛ النتيجة objection عند مخالفة معروفة أو needs_review عند الحاجة إلى مراجعة. اجتياز بعض الشروط ليس إثبات استحقاق. قبل اعتماد أي تجاوز يجب مطابقة المصدر وتوثيق سبب القرار؛ هذه النسخة لا تتحقق خارجياً من صحة تبرير المدير.

## تثبيت القرار وتغير البيانات

يحفظ الطلب لقطة مشفرة تشمل نسخة المحرك والسياسة والقواعد، هوية الموظف وحالته، المؤشرات والهدف والأساس السنوي، أسباب المراجعة، الفواتير والتحصيلات والمرتجعات التي تدعمها، وبصمة المحتوى. أسباب الطلب والقرار مشفرة أيضاً. تُقرأ اللقطة فقط تحت الصلاحيات المذكورة.

عند اتخاذ القرار يعيد الخادم الحساب تحت قفل الشركة والموظف. إذا تغيرت البيانات المؤثرة يعود 409؛ أعد التقييم واقرأ النتيجة الجديدة. decision يحمل reviewed_at وreview_token من التفاصيل ليمنع اتخاذ القرار من صفحة قديمة بعد إعادة التقييم. بعد الموافقة أو الرفض لا يمكن إعادة التقييم أو تغيير القرار؛ تبقى اللقطة أساس تفسير القرار التاريخي. لا يمكن تقديم طلب قيد المراجعة أو معتمد آخر لنفس الموظف والعملة والفترة الدقيقة؛ بعد رفض الطلب يمكن تقديم طلب جديد.

تُسجل العمليات في التدقيق، وترسل أحداث تقديم الطلب والقرار إلى outbox دون الراتب أو أسباب القرار. الكتابة تقبل Idempotency-Key؛ استخدمه لإعادة المحاولة الآمنة. الاشتراك المنتهي يمنع الكتابة ويترك القراءة حسب الصلاحيات.

## API

| المسار تحت /api/advisor | الوظيفة |
|---|---|
| GET /bonus-policies?page=1 | السياسات، 20 لكل صفحة |
| POST /bonus-policies | name, valid_from, valid_to, currency, mode، والنسب الثلاث كسلاسل عشرية |
| GET /bonus-requests?page=1 | ملخص الطلبات، 20 لكل صفحة دون لقطة كاملة |
| POST /bonus-requests | employee_uuid, policy_uuid, period_from, period_to, as_of, amount, reason |
| GET /bonus-requests/{uuid} | اللقطة والأسباب وreview_token وevaluated_at |
| POST /bonus-requests/{uuid}/evaluate | إعادة تقييم الطلب المعلق بنفس الفترة وتاريخ القياس |
| POST /bonus-requests/{uuid}/decision | decision=approve/reject، reason (12–2000 محرف)، reviewed_at، review_token |

الفترة القصوى 367 يوماً؛ period_from <= period_to <= as_of <= اليوم في منطقة الشركة الزمنية. amount سلسلة موجبة بدقة العملة المحددة في السياسة. UUID لشركة أخرى يرجع 404. self-decision أو تجاوز غير مخوّل يرجع 403. مبلغ أو سياسة خارج الحدود يرجع 422. طلب نهائي أو مكرر أو مراجعة قديمة يرجع 409.

## ما لم يكتمل

تأكيد تغطية المصدر، دفتر افتتاحيات وتعديلات ائتمانية عامة ورد الأموال، بيانات الحضور في المكافأة، السياسات متعددة المراحل، سياسات HR المتقدمة. أُضيف تفسير نوعي للتقارير من AI وتقارير محفوظة ومجدولة في ADVISOR-REPORTS.md؛ لا يؤثر AI في قرار المكافأة. هذه دورة مكافأة مبيعات أولية وليست جاهزية إطلاق تجاري؛ اختبارات MySQL/Redis والتزامن ومصالحة بيانات شركة فعلية مطلوبة قبل التشغيل الإنتاجي.
