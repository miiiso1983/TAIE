# التكامل مع البرامج الأخرى — بوابة البيانات v1

## المنفذ

بوابة استقبال JSON موحّد لكل مصدر داخل كل شركة، وتعريف مصادر Teami Pro وMaxCon وOdoo والبيان والخازن أو برنامج آخر. هذه أسماء مصادر وليست محوّلات أصلية جاهزة. لا يوجد سحب تلقائي أو اتصال خارجي أو تخزين كلمات مرور في هذه المرحلة.

مركز «التكاملات» يتيح تعريف المصدر، تعطيله وتفعيله، فحص دفعة JSON واعتمادها صراحة، وعرض آخر 20 دفعة للمصدر. يمكن متابعة بقية الدفعات عبر API المرقّم. الملفات CSV/XLSX ومسار ربط الأعمدة موجودان أيضاً في «بيانات الشركة».

## واجهات API

جميع الطلبات تستخدم مصادقة Sanctum وX-Tenant واشتراك الشركة الفعّال وفق إعداد الفوترة. أنشئ مستخدماً تقنياً محدود الصلاحيات لكل تكامل؛ لا تستخدم حساب المالك. لا توجد بعد رموز وصول مقيدة باتصال واحد؛ صلاحية integration.sync تسمح بكل مصادر الشركة المسموحة. لا ترسل مفتاح مزود أو كلمة مرور ضمن records.

| الطلب | الوظيفة | الصلاحيات الإضافية |
|---|---|---|
| GET /api/integrations/catalog | أسماء البرامج والبروتوكول المتاح | integration.read + data.sensitive.read |
| GET /api/integrations/connections | المصادر بصفحات 20 | نفسها |
| POST /api/integrations/connections | name وprovider | integration.manage + Idempotency-Key |
| PATCH /api/integrations/connections/{uuid}/status | status: active أو disabled | integration.manage + Idempotency-Key |
| GET /api/integrations/connections/{uuid}/batches | سجل الدفعات بصفحات 20 | صلاحيات القراءة |
| POST /api/integrations/connections/{uuid}/preview | فحص JSON قبل الكتابة | integration.sync + data.import.manage + صلاحية نوع البيانات + Idempotency-Key |
| POST /api/advisor/imports/{batch_uuid}/commit | اعتماد الدفعة ذرّياً | integration.read + integration.sync + data.import.manage + data.sensitive.read + صلاحية نوع البيانات + Idempotency-Key |

provider: teami_pro / maxcon / odoo / al_bayan / al_khazen / custom. source_system يولّد تلقائياً ويثبت للاتصال. بادئة int_ محجوزة؛ لا يمكن انتحالها عبر استيراد الملفات.

```json
{
  "schema_version": 1,
  "kind": "customers",
  "records": [
    {"customer_number": "C1", "name": "عميل تجريبي", "email": ""}
  ]
}
```

القوالب من GET /api/advisor/imports/schemas. الأنواع الحالية: employees/customers/invoices/receipts/returns/targets/compensation. كل قيمة حقل نص UTF-8؛ المبالغ نصوص عشرية بلا فواصل آلاف. لا ترسل حقولاً إضافية. الحد 1000 سجل و1 MiB لكل طلب. الدفعة المشفرة صالحة 7 أيام. preview لا يكتب سجلات أعمال؛ commit يعيد فحص أحدث البيانات ثم يكتبها في معاملة واحدة. المراجعة والاعتماد منفصلان، ولا يوجد اعتماد آلي.

## الهوية والتكرار

- الدفعة المتطابقة داخل المصدر والنوع تعيد الهوية نفسها. إعادة إرسال المستوردة تعيد imported.
- الفواتير والتحصيل والمرتجعات والأهداف تستخدم external_id ضمن مصدر الشركة. إعادة معرّف موجود ببيانات مختلفة تعطي خطأ؛ لا يوجد upsert صامت أو استبدال لسجل مالي.
- أرقام الموظفين والعملاء هويات مشتركة داخل الشركة، وليست معرّفات خاصة بالمصدر. على المحوّل الخارجي تحويل معرّفات البرامج إلى أرقام الشركة الموحدة. لم يُنفذ بعد جدول مطابقة متعدد البرامج لهذه الهويات.
- لا تستورد الفاتورة نفسها من برنامجين مختلفين باعتبارهما مصدرين مستقلين؛ عيّن مصدر الحقيقة لكل نوع بيانات قبل المزامنة.
- التعطيل يمنع فحص الدفعات واعتماد الدفعات المنتظرة، حتى عبر رابط الاعتماد القديم. لا يحذف البيانات المستوردة.
- سجل الدفعات يحتفظ بحالات validated/invalid/imported/expired، وعدد السجلات والأخطاء. طلب HTTP مرفوض قبل إنشاء الدفعة ليس محاولة مزامنة محفوظة في هذا السجل.

## المرحلة التالية: محوّلات البرامج

| البرنامج | المطلوب قبل بناء المحوّل |
|---|---|
| Teami Pro | توثيق endpoints، مصادقة وصلاحيات، شركة اختبار، حقول المستخدمين والعملاء والزيارات والأهداف |
| MaxCon | توثيق API أو وصول إلى كودها، فواتير وتفاصيل منتجات ومرتجعات وتحصيل ومخزون، شركة اختبار |
| Odoo | الإصدار والاستضافة وإتاحة API والوحدات المثبتة والشركات المسموحة؛ لا نفترض توافق البروتوكول بين الإصدارات |
| البيان والخازن | اسم المورد والإصدار وتوثيق الربط أو تصدير CSV/XLSX مع عينة مجهولة الهوية؛ لا نفترض وجود API عام |

مرجع Odoo الرسمي: https://www.odoo.com/documentation/19.0/developer/reference/external_api.html — الإصدار 19 يوثق JSON-2؛ يلزم التحقق من إتاحة API وفق اشتراك العميل وبيئته.

الترتيب المقترح: Teami Pro وMaxCon أولاً، ثم Odoo، ثم البيان والخازن حسب واجهات المورد. لكل محوّل: مطابقة حقول ومعرّفات، مصدر حقيقة، مؤشر مزامنة وحذف/إلغاء، جدولة ومحاولات إعادة مع تأخير، صفحة مقارنة أعداد وإجماليات مع المصدر، ثم تجربة شركة حقيقية. الربط الحالي باتجاه البرامج → تيمي؛ إعادة النتائج أو تعديل الرواتب والفواتير في المصدر يتطلب مسار موافقات مستقل.

## بيانات التوقعات المطلوبة لاحقاً

البوابة الحالية تستقبل إجماليات الفواتير فقط ولا تنفذ توقع المنتج. قبل forecast المنتجات يلزم توسيع القالب إلى المنتجات وبنود الفواتير والكميات والمخزون والأسعار والمواسم، وموقع العميل/التسليم (المحافظة والمدينة والمنطقة) وهويتها الموحدة؛ بيانات السكان تكون مصدراً مستقلاً مؤرخاً. لا نستنتج موقع الطلب من مخزن الفاتورة.
